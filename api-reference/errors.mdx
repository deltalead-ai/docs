La API de DeltaLead usa códigos de estado HTTP estándar para señalar el resultado de cada solicitud. Cuando una solicitud falla, la respuesta incluye un cuerpo JSON con dos campos garantizados: `status`, siempre con el valor `"error"`, y `detail`, un identificador estable en `snake_case`. La lógica de manejo de errores debe ramificar según ese identificador y nunca según texto libre.

## Formato de la respuesta de error

Todas las respuestas de error siguen esta forma:

```json
{
  "status": "error",
  "detail": "lead_not_found"
}
```

<ResponseField name="status" type="string">
  Siempre `"error"` en una respuesta fallida. Permite distinguir un error de una respuesta exitosa sin mirar el código de estado HTTP.
</ResponseField>

<ResponseField name="detail" type="string">
  Identificador estable del error, en `snake_case` y legible por máquina. Este es el campo a usar en la lógica de manejo de errores.
</ResponseField>

El cuerpo no replica el código de estado HTTP: ese dato ya viaja en la respuesta y duplicarlo solo abre la puerta a que las dos fuentes se contradigan.

## Códigos de estado HTTP

| Estado | Significado |
|---|---|
| `200 OK` | La solicitud fue exitosa |
| `201 Created` | Recurso creado correctamente |
| `202 Accepted` | La solicitud se aceptó y se procesa de forma asíncrona |
| `400 Bad Request` | Parámetros inválidos: revisar `detail` |
| `401 Unauthorized` | Clave de API ausente, inválida, vencida o revocada |
| `403 Forbidden` | Clave válida pero la cuenta asociada está suspendida |
| `404 Not Found` | El recurso no existe |
| `422 Unprocessable Entity` | Falló la validación: revisar el arreglo `errors` para los errores por campo |
| `429 Too Many Requests` | Límite de tasa superado: reintentar después de `Retry-After` |
| `500 Internal Server Error` | Error del servidor de DeltaLead: reintentar con backoff exponencial |

Crear un lead cuyos datos de contacto ya existen no produce un conflicto. Los datos se resuelven sobre el lead existente —es la misma semántica de merge que aplica el [Custom Webhook](/api-reference/webhooks/custom-inbound)— y la respuesta devuelve ese lead en lugar de crear un duplicado.

## Errores de validación (422)

Cuando falla la validación del cuerpo de la solicitud, la API devuelve una respuesta `422` con un arreglo `errors` al mismo nivel que `detail`, que indica con precisión qué campos son inválidos. Recorrer `errors` permite mostrar mensajes por campo a los usuarios o en los logs.

```json
{
  "status": "error",
  "detail": "validation_error",
  "errors": [
    { "field": "contact.phone", "detail": "invalid_phone_format" }
  ]
}
```

<ResponseField name="errors" type="array">
  Presente solo en respuestas `422`. Cada elemento contiene una clave `field` (la ruta dentro del cuerpo de la solicitud que falló) y una clave `detail` con el identificador de la regla de validación incumplida.
</ResponseField>

Causas habituales de un `422`:

- Números de teléfono que no están en [formato E.164](https://en.wikipedia.org/wiki/E.164) (por ejemplo, `+5491122334455` es válido; `011 2233-4455` no)
- Campos obligatorios ausentes en el cuerpo de la solicitud, como un `contact` sin `email` ni `phone`
- Valores de enumeración fuera del conjunto permitido (por ejemplo, un valor de `status` no reconocido)
- Cadenas de fecha y hora que no siguen el formato ISO 8601

## Límite de tasa (429)

El límite es de 5 solicitudes por segundo sostenidas por clave de API, con una ráfaga de hasta 10. Al superarlo, la API devuelve `429 Too Many Requests` con una cabecera `Retry-After` que indica cuántos segundos esperar antes de reintentar. Es la única cabecera de recuperación que emite la API.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 14
```

Conviene implementar **backoff exponencial** en todas las solicitudes que se reintentan: esperar los segundos indicados en `Retry-After` en el primer reintento y luego duplicar el tiempo de espera en cada intento posterior (con un tope máximo, por ejemplo 60 segundos), hasta que la solicitud tenga éxito o se agote el presupuesto de reintentos.

## Errores de servidor (500)

Un `500 Internal Server Error` indica una falla transitoria en la infraestructura de DeltaLead. Corresponde reintentar la solicitud con backoff exponencial: la gran mayoría de los errores transitorios se resuelve en pocos segundos. Si un `500` persiste durante más de unos minutos, se puede consultar la [página de estado de DeltaLead](https://deltalead.instatus.com/) o contactar a soporte.

<Tip>
  Conviene registrar siempre el **cuerpo completo de la respuesta de error**, no solo el código de estado HTTP. El campo `detail` es legible por máquina y estable entre versiones de la API, lo que lo hace apto para reglas de alerta y remediación automática. Por ejemplo, se puede detectar `lead_not_found` y omitir el registro, o capturar `validation_error` y mostrar el arreglo `errors` directamente en el panel de un operador.
</Tip>
